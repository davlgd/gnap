Delegate access to a folder, then change your mind

A client asks for read access to a synthetic folder and archive. You decide as the resource owner, then watch what each choice does to the grant and its tokens.

A public sandbox with synthetic data. It shows a restricted GNAP profile with HTTP message signatures, not complete coverage or a certification. The client, the authorization server and the resource servers run in one deployment, but they exchange real signed HTTP requests.

1Choose a scenario

Every scenario starts a fresh grant request from the client. No client secret or private key reaches your browser.

Proof for the next start

The method holds for the whole grant: to change it, start again. Identity disclosure and the server-to-client callback use HTTP message signatures in this lab.

  • Consent in this browser

    The client asks for the folder and the archive, and you decide on the authorization server's page.

  • Consent on a second screen

    You enter a short code in another browser instead of following a redirect, and the client polls for your decision.

  • Two tokens in one request

    One consent covers a documents token and a reports token, which you can approve together or approve the reports one alone.

  • Disclose a fictional identity

    The client also asks who the resource owner is, and receives a signed assertion about the sandbox's one fictional subject. HTTPS only.

  • Finish with a server-to-client callback

    Consent happens in this browser, but the authorization server sends the finish notification straight to the client over HTTP.

Go to the grant state

Allowing this request also discloses the fictional subject to this application, as opaque and issuer-and-subject identifiers and a five-minute ID Token. Denying releases neither the identity nor a token. Approval closes the grant's continuation: its resource token can still be used or revoked, but the grant can't be changed or polled.

3Use the access

Each resource server asks the authorization server about the token, with its own key (RFC 9767), then checks the caller's signature, the exact right, and the expiry. Neither token values nor private keys ever reach this page.

What each action does

Two tokens from one request each have their own rights, resource server and management: rotating or revoking one leaves the other alone, and neither works at the other's resource. The metadata read lets the folder server obtain a separate token for a second server, with one read right, bound to the folder server's key, for at most 60 seconds; the folder server tries to revoke it after the call. An exchange that can't complete refuses access for now with 503, which differs from a refused token or proof (401). Parent tokens and browser sessions last at most 20 minutes.

4Change or end the grant

A reduction within the live rights is approved directly; an expansion asks you again, and the earlier tokens keep working until you decide. Approving replaces them all. A denial closes the continuation without revoking those earlier tokens.

Go to the grant state

You can cancel a pending request, or revoke an approved grant, while its continuation is open and once the wait period has passed.
