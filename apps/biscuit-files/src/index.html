Narrow a token yourself, then retire it

The authorization server issues this client a Biscuit access token for two synthetic files. The client can add restrictive blocks to the token on its own, and the file server checks every block on each signed request.

A public sandbox with synthetic data. Three processes exchange real signed HTTP requests. The authorization server grants with a fixed demonstration policy and asks no resource owner for consent. This is a bounded example, not complete coverage or a certification.

1Request and use access

The authorization server grants read the notes and write the draft for 20 minutes. Every visitor's session starts with the client's one configured key.

2Restrict locally

Add a block that limits the token to one file until a given time. The client does it alone, with no round trip to the authorization server, and its key doesn't change.

Each block narrows the token further, and blocks intersect: a block for the notes, then one for the draft, allows neither file. No block grants a new right. A token takes eight blocks at most.

Go to the session

3Renew and retire access

A rotation gives the client a new token with the rights the authorization server approved, without the restrictive blocks. A revocation ends the token.

Check what was retired

A key change proves the old and new keys together, and the new key stays in the client process. A session makes three key-generation attempts at most, failed ones included, and the client process four per minute across sessions.

On each request, the file server asks the authorization server about the token's authority and reserves the request's nonce once for its presentation key. No positive decision is cached. This channel is the example's own, not GNAP introspection, and a single block can't be revoked.
