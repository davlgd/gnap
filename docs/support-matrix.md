# Support matrix

This page lists what the libraries and applications support, how far, and the tests that show it. Use it to check whether a capability you need is available before you integrate, and to find its limits. It's a capability inventory, not a conformance score: no row claims that a whole RFC section, an interoperability profile, or production readiness is complete.

## How to read it

The **RFC condition** column says when GNAP requires a capability. *C1/C2 required* marks a capability that the Web-Based Redirection or Secondary Device profile of [RFC 9635 Appendix C](https://www.rfc-editor.org/rfc/rfc9635.html#appendix-C) requires. *Conditional* means the rules of the cited section apply once you use that message, endpoint, or format, without an obligation to implement every option. A *deployment responsibility* is left to your deployment by the protocol, without exempting it from security checks.

The **project decision** column says what this project aims to support, which isn't the same as what GNAP requires. The **state** is *implemented and tested*, *partial*, *model only* when the data types exist without a working implementation, or *missing*. Only a test or a recorded execution supports a claim that a behavior works.

Every exchange below runs between this project's own roles, so none of it establishes interoperability with an independent implementation. The [evidence ledger](../conformance/README.md) keeps the RFC's normative text block by block, and maps reviewed observations to those blocks.

## Decisions

- Biscuit is a required target: support means issuing, validating, and attenuating tokens in a working application
- Signed and encrypted JWT access tokens are allowed alternatives, for a concrete integration
- Macaroon and ZCAP tokens are out of scope, and their registry names stay as reference data
- HTTP Message Signatures (`httpsig`) are the preferred proof method
- Ed25519 and ECDSA P-256 request signatures are supported, next to RSA-PSS
- The `jws` and `jwsd` proof methods are selected targets, with RS256, ES256, and EdDSA
- mTLS is an allowed additional proof method, not a prerequisite
- Opaque reference tokens are the baseline of the libraries and of the delegation lab

mTLS needs a real TLS client-certificate trust boundary: accepting a forwarded certificate header isn't mTLS support. A distributed application doesn't force every token through a shared store, nor assume that introspection is the only way to validate one. Biscuit tokens need an explicit mapping of GNAP rights, audience, expiry, and key binding to their policy, and a revocation policy for local validation.

## Token formats

The authorization server and the resource server agree on a format. [RFC 9767 §2.2](https://www.rfc-editor.org/rfc/rfc9767.html#section-2.2) defines the registered names, and GNAP doesn't require an implementation to support every one.

## What this page doesn't establish

These rows don't establish complete support for an RFC section, for either interoperability profile of Appendix C, or for production use. A test between this project's roles shows that they agree with each other, not that an independent implementation would. The [releasing guide](releasing.md) covers what a crate release needs, which is separate from expanding protocol support.
